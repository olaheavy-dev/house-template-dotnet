# Backend (.NET)

Owned by house-template-dotnet. Before using an ASP.NET Core, EF Core or .NET API, check the official docs for the pinned version through the Microsoft Learn MCP server (`.mcp.json`) or `docs/references/dotnet.md`; don't rely on memory.

- **Layout:** a modular monolith in `backend/` (`Backend.slnx`). `src/Common/` is the shared kernel (`Common.Domain`, `Common.Application`, `Common.Infrastructure`, `Common.Presentation`); each module under `src/Modules/<Name>/` has six projects: `Domain`, `Application`, `Infrastructure`, `Presentation`, `IntegrationEvents` and `PublicApi`. `src/Api/Api` is the host. Project and namespace names are the same in every app (`Common.Domain`, `Modules.Platform.Application`).
- **New modules:** `make module NAME=<Name>` (the `add-module` skill); never copy a module by hand.
- **Architecture tests** (`backend/tests/ArchitectureTests`, ArchUnitNET) enforce the rules below and the module layout, and run in Debug as well as Release (Release optimisations can hide a dependency). Every rule in `HouseRules.cs` has a planted violation in `ArchitectureTests.Fixtures` that its self-test must find: a new rule comes with one. Never weaken a rule to make a change pass; change the code.
- **Boundaries:** a module never references another module's projects except its `IntegrationEvents` and `PublicApi`. Domain depends on nothing but `Common.Domain`; Application on its Domain and `Common.Application`; Presentation on its Application and `Common.Presentation`; Infrastructure wires the module up (`Add<Name>Module`).
- **Requests:** handlers use Immediate.Handlers (source-generated, MIT; no MediatR): an `internal` `[Handler]` partial class in the module's Application project with a private `HandleAsync(TRequest, CancellationToken)` returning `ValueTask<ErrorOr<T>>`; the request type is a public record. Endpoints depend on `IHandler<TRequest, ErrorOr<T>>`, never on the handler class. Each module's Application assembly declares its pipeline once (`[assembly: Behaviors(typeof(LoggingBehavior<,>), typeof(ValidationBehavior<,>))]`); requests get a FluentValidation `AbstractValidator<T>`, and an invalid one is answered with validation errors before the handler runs. The module registers with its generated `Add<Assembly>Handlers()` and `AddValidatorsFromAssembly(..., includeInternalTypes: true)`. The package's own analyzer (IHR…) flags handler mistakes at build time.
- **Time:** take `TimeProvider` from DI; `DateTime.Now`, `UtcNow`, `Today` and their `DateTimeOffset` forms fail the architecture tests. Store and pass `DateTimeOffset`.
- **Integration events:** public records whose every property is set by the constructor (an unset property is always empty on the wire).
- **Results:** expected failures are values, never exceptions: handlers return `ErrorOr<T>` (`ErrorOr<Success>` for commands without a value) with `Error.NotFound("area.reason", "…")` and friends, the code stable and machine-readable. Endpoints answer with `ApiResults.Ok(result)`, `ApiResults.NoContent(result)` or `ApiResults.Problem(errors)` (RFC 9457: the first error sets the status and its code is the `code` extension; validation errors become one problem listing every field). Exceptions are for bugs and broken infrastructure.
- **Lists:** cursor (keyset) pagination, never offsets: `GET .../things?limit=20&cursor=...` answers `{ "items": [...], "nextCursor": "..." | null }`. The endpoint binds `[AsParameters] PageQuery` (`Common.Presentation`) and passes `page.ToRequest()` in the query; the query's validator adds `RuleFor(query => query.Page).SetValidator(new PageRequestValidator())` (limit 1 to 100, default 20; cursor up to 512 characters); the handler decodes the cursor with `Cursor.Decode<TKey>(...)` (a damaged one is a 400 validation error on `cursor`), asks the store for `limit + 1` rows ordered by the key, and returns `Page.From(rows, request, row => key, row => response)`. Sort by a unique, stable key (Platform's notes use their UUIDv7 id), and scope the query to the signed-in user. `ListNotes` is the example. Pages stay stable while rows are added and deep pages cost no more than the first.
- **Idempotency-Key:** a POST that a client may retry opts in with `.WithIdempotencyKey()` (`required: true` makes a request without the header a 400, `idempotency.key_required`). The first request with a key runs and its response (not a 5xx, not over `Idempotency:MaxResponseBytes`) is kept for `Idempotency:KeyTtlHours` (24); the same request again gets it back with `Idempotency-Replayed: true`; the same key with a different method, path, query or body is a 422 (`idempotency.key_reused`); one still running is a 409 with `Retry-After` (`idempotency.in_progress`), and after `Idempotency:LockSeconds` (60) a retry takes the key over. A key belongs to the signed-in user (else the caller's address). Keys are 1 to 255 printable characters. State lives in the shared kernel's `common` schema (`IIdempotencyStore`, `CommonDbContext`, migrated by `make migrate` like a module's); `app.UseIdempotency()` runs after authorization. It is a record of the HTTP exchange, not of the work: an endpoint must still be safe if its response is lost. GET, HEAD and OPTIONS pass through. Expired rows are removed when their key is reused; sweep `common.idempotency_keys` by `ExpiresAt` if volume ever matters.
- **Endpoints:** plain minimal APIs, one `internal static class <Feature>Endpoint` per feature in the module's Presentation project with a `static void Map<Feature>(this IEndpointRouteBuilder app)`, routes under `v1/`. The module's `<Module>Endpoints.cs` calls each one and `Program.cs` calls `app.Map<Module>Endpoints()`; an architecture test fails on an endpoint that is never called.
- **Errors on the wire:** every error is a problem (`application/problem+json`) with a `traceId`: the ones endpoints return, a status with no body (an unknown route's 404) and an unhandled exception, which becomes a 500 with the code `internal.unexpected` and no detail; the exception is logged, never shown (`Common.Presentation/ProblemDetailsSetup.cs`).
- **Service defaults:** `src/Api/ServiceDefaults` gives every process (`builder.AddServiceDefaults()`, `app.UseServiceDefaults()`) OpenTelemetry traces, metrics and logs, exported over OTLP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; JSON console logs outside development; an `X-Request-ID` on every response (the caller's when it looks like an id), logged as `RequestId` beside the `TraceId`; one access line per request with the route template, never the raw path or query string (ASP.NET Core's hosting diagnostics are off: they log both); and the standard resilience handler (retries, circuit breaker, timeouts) on every `HttpClient` from `IHttpClientFactory`. Get clients from the factory, never `new HttpClient()`. Log with source-generated `[LoggerMessage]` methods, and never log request bodies, tokens or personal data.
- **Settings:** a setting the app can't run without is an options class bound with `AddValidatedOptions<T>(section)` (`Common.Infrastructure`), which checks its data annotations at start-up; add `.Validate(...)` for rules they can't express. Annotations on a nested object aren't checked, so keep options flat. Document each one in `backend/.env.example`.
- **Limits** (`src/Api/Api/Hardening.cs`, settings in `ApiOptions`): a request body over `Api:MaxRequestBodyBytes` gets a 413, a request over `Api:RequestTimeoutSeconds` a 504, and a caller over `Api:RateLimitPerMinute` (per signed-in user, otherwise per address) a 429 with `Retry-After`, all as problems. CORS answers only the origins in `Api:CorsOrigins`; `AllowedHosts` lists the host headers served. Every response gets the API security headers and `Cache-Control: no-store` (NetEscapades.AspNetCore.SecurityHeaders); an endpoint that needs others gets a named policy with `.WithSecurityHeadersPolicy(...)`.
- **Sign-in and permissions** (`src/Api/Api/Auth.cs`): the API accepts bearer tokens from `Auth:Issuer` for the audience `Auth:Audience` (Keycloak locally, `backend/keycloak`); with no issuer every protected endpoint answers 401. A permission is a role of the API's client (`me.read`), read only from `resource_access.api.roles` (a `permission` claim in the token itself is dropped); an endpoint requires one with `.RequirePermission(ModulePermissions.X)` (`Common.Presentation.SignedInUser`), giving 401 to anonymous callers and 403 without it, both as problems with codes `auth.unauthenticated` and `auth.forbidden`. Declare a module's permissions in `<Module>Permissions` and add each as a client role in `backend/keycloak/realm.json`. The user's id is the token's `sub` (`SignedInUser.IdClaim`), never an email. In Development only, `X-Dev-User: <id>` stands in for a signed-in user with every permission (`X-Dev-Permissions: a,b` narrows them), as in the FastAPI layer; never rely on it elsewhere. `GET /v1/me` is the example protected endpoint.
- **Data:** one Postgres for every module, `ConnectionStrings:Default`; each module keeps its tables and its `__ef_migrations` history in its own schema (the module's name, lower-case) and never reads another module's tables or has a foreign key into them. A module's `DbContext` lives in Infrastructure and is registered with `AddModuleDbContext<T>(configuration, schema)` (`Common.Infrastructure.Persistence`), which adds audit timestamps and a readiness check named `database:<schema>`. Entities derive from `Common.Domain.Entity` (id, `CreatedAt`/`UpdatedAt` stamped from `TimeProvider` on every save, `Version` as Postgres' `xmin`, so a stale save throws `DbUpdateConcurrencyException`); call `modelBuilder.ApplyEntityConventions()` last in `OnModelCreating`. Application code asks for a store interface it declares (`INoteStore`); Infrastructure implements it, so Domain and Application never see EF Core. `Platform`'s `Note` is the example, and `make module` gives every new module the same wiring (`<Name>DbContext`, factory, an example `<Name>Item`, and an `Initial` migration it generates). `MigrateModuleDatabasesAsync()` applies every registered module's migrations for tests and local runs that start the host. Change the model, then `dotnet ef migrations add <Name> --project <module's Infrastructure project> --output-dir Persistence/Migrations` and commit the migration (migrations are generated code, left out of analysis). A module with a database has a `Persistence/<Module>DbContextFactory.cs` so `dotnet ef` and `make migrate` find it. `make migrate` applies them, `make migrate-bundle` builds one executable per module for a deploy, and `make seed` runs the modules' `IDataSeeder`s (development only, safe to repeat).
- **Integration events:** a module publishes through `IUnitOfWork` (`Common.Application`): `await store.PublishAsync(new NoteCreated(...), ct)` then `await store.SaveChangesAsync(ct)`. The event is stored in the same transaction as the module's data (transactional outbox) and delivered after it commits, at least once; a failed save delivers nothing. A module's store derives from `OutboxUnitOfWork<TContext>` and takes `ModuleOutbox<TContext>`. A subscriber is a public class named `*Consumer` or `*Handler` in the module's Infrastructure project with a `static Handle(TEvent, ...)` method; the module registers its assembly with `AddIntegrationEventSubscribers(...)`. Modules never reference `Wolverine` (an architecture test enforces it); only `Common.Infrastructure` and the host do. Wolverine's glue code for the host is generated ahead of time into `src/Api/Api/Internal/Generated` and compiled in: **run `make codegen` after adding or changing a subscriber and commit the result** (`make check` fails when it is stale, and a Release build fails to start the app when a handler has no generated code). Debug builds carry the compiler and generate on the fly, so a new handler works before `make codegen`. The API needs its database to start (messaging registers the node there); `/health/ready` still reports it going away later.
- **Caching:** inject `HybridCache` (Microsoft.Extensions.Caching.Hybrid) and read through `cache.GetOrCreateAsync(key, factory, cancellationToken: ct)`: each instance keeps entries in memory, concurrent first reads of a key run the factory once, and with `ConnectionStrings:Cache` set (Valkey or Redis) instances also share one second-level cache. Without that setting nothing else is needed. There is **no cross-instance invalidation**: a removal clears the shared entry, but another instance serves its in-memory copy until `LocalExpirationMinutes` pass, so keep that short for anything that changes. A shared cache that is down costs a read milliseconds (the multiplexer fails fast and gives up after `SharedTimeoutMilliseconds`), and the read goes to the source. Settings under `Cache` (`ExpirationMinutes` 5, `LocalExpirationMinutes` 1, `MaximumPayloadBytes` 1 MiB, applied to what is written to the shared cache, `SharedTimeoutMilliseconds` 100, `KeyPrefix` `app:`). Do not remember a miss: a handler that finds nothing calls `cache.RemoveAsync(key)` (`GetNote` does), or the cache hides the entry when it appears. The factory runs once for every request waiting on the key and may outlive the request that started it (a disconnect ends that request, and its scope with it), so it must not use anything scoped to a request: read through a singleton that opens its own scope per lookup (`INoteReader`), not the request's store or `DbContext`. Cache plain data records that serialize, never entities; put what makes the entry specific in the key (`platform:note:<id>`) and keep authorization checks outside the cache (every read still checks the owner). A handler that changes what is cached calls `cache.RemoveAsync(key)` (or `RemoveByTagAsync`) after it saves. `GetNote` is the example. A shared cache can serve data that is gone from the database until it expires, so keep expiries short for anything a user would notice.
- **Feature flags:** Microsoft.FeatureManagement.AspNetCore 4.8.0, flags in configuration in Microsoft's `feature_management:feature_flags` schema (appsettings in development; in production environment variables such as `feature_management__feature_flags__0__id=notes-list` and `feature_management__feature_flags__0__enabled=false`). Handlers ask `IFeatureFlags` (`Common.Application`: `IsEnabledAsync`, `VariantAsync`), never the library; one snapshot per request, so a flag reads the same throughout it; a flag that is not defined is off. Endpoints take a flag away with `.WithFeatureGate(Flag)` (a disabled feature answers 404 as a problem; it must be the last call in the endpoint chain, because it returns the plain builder). The percentage (`Microsoft.Percentage`), time-window (`Microsoft.TimeWindow`) and targeting (`Microsoft.Targeting`) filters are on; targeting sees the signed-in user: the user id is the token's `sub` and the groups are the user's permissions, so a flag can be aimed at a person or at everyone holding a permission (nobody signed in is nobody targeted). Variants (`variants` and `allocation`) give each user a name, which is how a share of users is moved to another model or provider. A flag with `telemetry.enabled` leaves its evaluation as an event on the request's trace. `GET /v1/flags` (permission `flags.read`) returns `{ "flags": [{ "key", "enabled", "variant" }] }` for the flags in `Flags:Public` only, evaluated for the signed-in user and never with their rules; a front end reads it through its proxy. Declare a module's flag names in `<Module>Flags`. Tests set flags with settings (`feature_management:feature_flags:0:enabled`). `notes-list` is the example. Upgrade path without code changes beyond `IFeatureFlags`: a Postgres flag store (an `IFeatureDefinitionProvider`) for flags changed at runtime, or Azure App Configuration.
- **Streams:** push updates with Server-Sent Events (`TypedResults.ServerSentEvents`), not SignalR: give each event an id and resume after `Last-Event-ID`, mark the endpoint `.DisableRequestTimeout()`, and end the stream when the host starts to stop (`IHostApplicationLifetime.ApplicationStopping` linked into the loop), or every connected stream holds a deploy up for the whole 30-second shutdown timeout; the client's `EventSource` reconnects to another replica. `PingStreamEndpoint` is the example.
- **Image and Compose:** `backend/Dockerfile` (build it from the project root: `make image`) restores in locked mode, publishes the API without tests and runs it on `aspnet:10.0-noble-chiseled`, pinned by digest: no shell, a non-root user, port 8080. `GIT_COMMIT` (a build argument, `make` passes the short hash) is shown by `/health/live`. The image runs `dotnet Api.dll`, and has two more commands: `healthcheck` (the image's HEALTHCHECK; there is no curl) and `migrate`, which brings every module's tables and the messaging tables up to date and exits. **Outside Development the API never changes the schema:** a deploy runs `migrate` once from the same image before the new version starts (compose does; Kubernetes: a Job or init step), and an API started without the messaging tables refuses to start with an error naming them. `backend/compose.yaml` (included by the root `compose.yaml`) is production-shaped and on loopback with every image pinned by digest: `db` (PostgreSQL 17), `keycloak` (26.8.1, the realm imported from `backend/keycloak/realm.json`, only when the realm does not exist yet: after editing it, `docker compose rm -sfv keycloak && docker compose up -d keycloak`), `dashboard` (Aspire: traces and logs at http://localhost:18888), `valkey` (the optional shared cache, profile `cache`), `migrate`, `worker` (profile `worker`: the same image started with `--role=worker`, see below) and `api` (http://127.0.0.1:8000, `stop_grace_period` 35 s to match the host's 30-second shutdown). `make up` runs it all, `make db-up` starts only what the API needs on the host (`make migrate && make dev-backend`), `make down` stops it. The compose API runs as Production: sign in with a Keycloak token (`dev`/`dev`, see `backend/keycloak/README.md`); `X-Dev-User` does not work there.
- **Health:** `/health/live` touches no dependency; `/health/ready` runs the checks tagged `ReadinessChecks.Tag` and answers 503 with the failing names. A module whose dependency the API can't serve without adds a check with that tag.
- **OpenAPI:** the build writes `backend/openapi/v1.json` (Microsoft.AspNetCore.OpenApi; no Swashbuckle or NSwag); commit it with the change that moved it. The Next.js layer generates its client from it, and `make check` fails when it is stale (`make openapi-backend` rewrites it). Describe each endpoint with `.WithName(...)`, `.WithTags(...)` and `.Produces<T>()`/`.ProducesProblem(...)`; XML doc comments on request and response types become schema descriptions. In development, `/openapi/v1.json` serves it live and `/scalar` shows it.
- **InspectCode and frameworks:** when a framework uses a member InspectCode can't see (a record only the JSON serializer reads), mark it `[UsedImplicitly]` (JetBrains.Annotations) with a comment saying who uses it, rather than adding an `.editorconfig` exception.
- **Build:** every analyzer warning is an error (`backend/Directory.Build.props`, `AnalysisMode=All`); the exceptions in `backend/.editorconfig` each say why. Fix findings rather than suppressing them; a new suppression needs a reason beside it.
- **Packages:** versions only in `backend/Directory.Packages.props` (central package management); after a change run `make lock-backend` and commit the lock files. Never `dotnet add package --source` an unvetted feed (`backend/nuget.config` maps every package to nuget.org). No MediatR, FluentAssertions or SonarAnalyzer: their licences changed.
- **Tests:** NUnit on Microsoft.Testing.Platform with NUnit's own assertions; names read `Method_condition_result`.
  - Unit tests per project (`tests/<Project>.UnitTests`): domain rules and handlers.
  - Acceptance tests (`tests/AcceptanceTests`): Reqnroll feature files in the product's words, one per feature, driving the API through `WebApplicationFactory<Program>`. A new endpoint comes with its scenarios.
  - Integration tests (`tests/IntegrationTests`): technical checks on the host (wire format, HTTP details).
  - A bug fix comes with a test that fails without it.
- **Supply chain:** `make check` fails on a licence outside `backend/licenses/allowed.json` and on any JetBrains InspectCode finding (exceptions in `backend/.editorconfig`, each with its reason). Before adding a package, check it in `docs/references/dotnet.md`'s terms: downloads, maintainers, last release, licence and an exit route; add a row there. `make package-health` flags packages with no release in a year; accept one only in `backend/package-health.json`, with a reason and an end date.
- `make check` is what CI runs: locked restore, `dotnet format` check, the Release build, the OpenAPI document up to date, licences, InspectCode, the tests with coverage, and the architecture tests in Debug. `make doctor-backend` checks the machine.
- **Worker role:** `dotnet Api.dll --role=worker` (or `ROLE=worker`; `api` is the default, anything else refuses to start) runs the same modules, messaging, caching, flags and telemetry with no API surface: no auth, OpenAPI, hardening, idempotency or module endpoints, only `/health/live` and `/health/ready`, so the image's HEALTHCHECK works unchanged. Messaging (Wolverine's outbox, inbox and durable queues) runs as hosted services of either role, so a worker recovers and processes what the outbox holds. With local queues only, a new event still runs in the process that published it; the worker pays off once there is a background job or a broker. `docker compose --profile worker up worker` runs it; scale the two apart in a deploy. Services that only the API role needs go inside `if (!isWorker)` in `Program.cs`.
- **Mutation testing:** `make mutation` runs Stryker.NET (`dotnet-stryker`, pinned in `.config/dotnet-tools.json`, on the Microsoft Testing Platform runner) over the code the unit tests cover: Common.Application and each module's Domain and Application, one unit test project at a time (`MUTATION_TARGETS` in `mk/dotnet.mk`; Stryker finds the code to mutate among a test project's **direct** project references, so a unit test project references the projects it tests). Integration and architecture tests are left out on purpose: they need Docker or are slow, and `--solution` mode ignores `--test-project` and runs them all. Code the integration tests cover (Common.Presentation, Infrastructure, the host) is not in the list: its unit-test score would be near zero and mean nothing. Settings and thresholds are in `backend/stryker-config.json` (break below 50 %, low 60, high 80); reports (HTML, JSON) land in `backend/StrykerOutput`. It runs weekly in `.github/workflows/mutation.yml` and on demand, not on pull requests, and fails when a project falls below the break threshold. A new module's unit tests join `MUTATION_TARGETS`. Survivors are tests that would not notice a change: strengthen the test, don't exclude the mutant.
